# Waddle data inventory (working document)

Checked against the app and schema on 2026-10-21. This records current behavior for the operator's policy and deletion decisions; it is not a public privacy policy. The daily cleanup schedule is active in production, and a manual run returned HTTP 200 on 2026-10-21.

| Data | Where and why | Who can access it now | Current removal behavior | Decision still needed |
| --- | --- | --- | --- | --- |
| Sign-in account, name and photo | Supabase Auth and `profiles` support sign-in and friend identity. | The account owner and people involved in a pending or accepted friend request can read a profile; Supabase processes auth data. | The account dialog offers self-service deletion. Linked rows cascade after group JSON is scrubbed. | Backup handling, age rule and privacy contact. |
| Friend requests | `friend_requests` stores a recipient email or phone number, note, sender and status, even before a recipient signs up. | Sender and addressed recipient through database rules. | Either party can remove a request; account deletion cascades linked rows. No automatic expiry is set. | Pending/declined request retention, non-member contact requests. |
| Groups, guests and plans | `workspaces.state` holds members/guest names, availability, ideas, photos, plans, votes, RSVPs, comments and snapshots for friend hangout counts. | The Waddle server checks membership or a live guest invite; signed-in members and invited guests see the data allowed by their view. A signed-in outsider with only the group URL is denied. | Account deletion removes linked member data from live group JSON; groups remain. Daily cleanup removes guest rows 90 days after last activity. Other members' content and external copies may remain. | Multi-admin roles, locked-group recovery, group retention and backups. |
| Calendar shares and presence | `calendar_shares`, `sharing_settings` and `presence` hold chosen event visibility, shared busy blocks and optional “Free now” notes. | The owner, authorized friends or the server as allowed by each database rule. | A user can stop a share or status. Rows linked to an Auth user cascade on user deletion; expired presence/share windows can remain stored. | Retention after expiry and treatment of shared copies. |
| Booking pages and visitors | `booking_pages` stores owner settings, busy ranges and up to three ICS URLs; `bookings` stores visitors' required name/email, optional note, time and cancel token. | The booking owner sees visitor details; the public API exposes only open times and booking/cancellation actions. Vercel and Supabase process requests. | Cancel changes status; daily cleanup deletes booking rows 90 days after cancellation or booked end, whichever is earlier. Deleting a booking page cascades its bookings. | ICS URL deletion and backups. |
| Google Calendar | The browser gets a short-lived access token in session storage; the server stores an encrypted refresh token in `google_tokens` for ongoing sync and booking free/busy checks. Event names/places pass through sync, but booking checks use times only. | The user's browser, Waddle's API and Google. Only the server service role can read the refresh-token row. | Disconnect now requires confirmed server token deletion before reporting success; browser token and imported events are then removed locally. | Whether to revoke the Google grant separately, and backup retention. |
| Push and notification records | `push_subscriptions` stores device endpoints/keys for opted-in notifications; `notification_log` stores send-deduplication keys and timestamps. | The account owner can manage their device rows; the server handles delivery and the log. Push service providers receive messages. | Device subscription may be removed; user deletion cascades subscriptions. Daily cleanup removes notification-log rows older than 90 days. | Failed endpoint retention and backups. |
| This device | Local/session storage keeps login state, preferences, cached group/calendar data and guest pass; service worker caches the app shell for offline use. Google access tokens now stay in session storage rather than persistent local storage. | The device's browser profile and anyone with access to it. | “Reset this device” clears app storage on that device, not Supabase records. Browser or app cache may persist until cleared/updated. | Exact storage list and user-facing deletion instructions. |

Services to describe in the eventual public policy: Supabase, Vercel, Google sign-in/Calendar and Google Fonts. Optional services must be listed only once enabled: Resend for booking email and the configured push delivery services. Confirm data locations and international transfers with the chosen service settings and intended audience before publication.

The operator prefers automatic expiry for unauthenticated guest and booking data, without a dedicated removal form. This does not replace an operator contact route for applicable privacy rights. Link the finished policy from the homepage, sign-in, guest join, booking page and footer. Document external email copies, caches, processor logs and backup retention separately from live database cleanup.
